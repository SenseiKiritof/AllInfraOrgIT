# ADR-003 — Keycloak authentication with BFF

- Status: accepted
- Date: 2026-10-25
- Decision: D6 confirmed on 2026-10-25 (realm `infraorgit`)

## Context

The original handles `state` and PKCE in the backend and stores tokens in HttpOnly cookies with `SameSite=Strict`; however, an explicit CSRF token is missing and the session remains a JWT in the browser, not a server-side session. A standard, testable flow is needed, with a server-side session and no token readable from JavaScript.

## Decision

- Keycloak 26, realm `infraorgit`, confidential client `infraorgit` with Authorization Code + PKCE S256.
- BFF in the API: `GET /auth/login`, `GET /auth/callback`, `POST /auth/logout`, `GET /api/session`.
- `state` and `code_verifier` in a short-lived HttpOnly cookie; server-side session with an `HttpOnly`, `Secure`, `SameSite=Lax` cookie, `__Host-` prefix in production.
- Server-side refresh with rotation; logout revokes the Keycloak session and deletes the cookie.
- Mutations with CSRF token and `Origin` check; no token in query string, localStorage or API response.
- Client secret only in the API.

## Alternatives considered

- **SPA with tokens in memory**: rejected, tokens readable from JavaScript and complex refresh.
- **Original's custom flow**: rejected, non-standard and coupled to local HTTP.

## Consequences

- The API is stateful for sessions: a shared store is needed to scale beyond one replica (decision in Phase 2).
- E2E tests with a real Keycloak are mandatory.
- Simpler CSP: the browser never talks directly to Keycloak for the APIs.

## Phase 1 verification

The legacy code confirms `state`/PKCE generated by the backend and tokens in HttpOnly cookies (`AuthCookies`), with `SameSite=Strict`. There is no CSRF token and no server-side session: the BFF remains a real change, but the jump is smaller than estimated in the plan.
