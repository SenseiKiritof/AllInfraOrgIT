## 1. Executive summary

The stack remains in good shape on the core controls:

- `make security-smoke` → **15 passed, 0 failed, 1 skipped** (rate-limit burst
  intentionally disabled).
- `dotnet list package --vulnerable --include-transitive` → no vulnerable
  packages for the API, tools or tests.
- `yarn audit --level high` (Web) and `npm audit --omit=dev` (Desktop) → **0
  vulnerabilities**.
- Session cookie: `__Host-infraorgit_session`, `HttpOnly`, `Secure`,
  `SameSite=Lax`; HSTS, CSP, frame denial and referrer policy present.
- TLS 1.1 rejected; 1.2/1.3 served by Caddy.
- No SQL/command injection, unsafe HTML rendering, `eval`, wildcard CORS or
  token in URL found in the reviewed paths.
- Standalone local API binds only `127.0.0.1`, rejects unauthenticated API
  calls, requires the per-launch bootstrap secret and still enforces CSRF.
- Import/export is SystemAdmin-only; import is limited to an empty local
  SQLite instance, uses a checksum, a dry-run token and a pre-import backup.

The material issue is **supply-chain integrity of the desktop updater**:
the previous report marked PT-11 fixed, but the current Electron updater only
compares a SHA-256 downloaded from the same unsigned GitHub release. A
compromised release can replace both the archive and its checksum. The old
signed-manifest implementation belonged to the retired Photino client.

New Low findings cover the plaintext fallback key, command scripts inside the
inventory export, and the fact that the import checksum proves integrity, not
authenticity.

## 3. Findings

### OW-01 — Medium (reopened PT-11) — Desktop updater trusts an unsigned release checksum

**Evidence:** `InfraOrgITDesktop/electron/updates.js:149-225` accepts the
`<archive>.sha256` asset from the same GitHub release and verifies only that
hash. `.github/workflows/publish.yml:1-6` states that packages are unsigned; no
signed manifest, public key or signature verification is present in the
Electron source. The signed-manifest implementation from the retired Photino
client (`src/InfraOrgIt.Desktop/Update/UpdateSignature.cs` in history) was not
ported.

**Impact:** An attacker who can replace the GitHub release, the release token
or the checksum asset can deliver a malicious archive that the in-app updater
accepts. TLS protects the transport, not the publisher identity. Manual install
has the same trust problem until the package is signed/notarized.

**Fix:** Sign a checksum manifest with a release key, embed the public key in
the app, verify it before trusting the archive hash, and with the same release
add Developer ID/notarization and Windows Authenticode. An unsigned package
should never be auto-installed.

**If skipped:** The updater remains a supply-chain path into every installed
desktop.

### OW-02 — Low — Inventory export includes free-text command scripts

**Evidence:** `InfraOrgITApi/src/InfraOrgIt.Api/Features/Data/DataTransferEndpoints.cs`
exports `CommandTemplates` and `ApplicationActions` in `InventoryData`;
`CommandTemplate.Script` and `ApplicationAction.CustomScript` are arbitrary
text and commonly contain credentials or tokens. `GET /api/data/export` returns
the file as plain JSON.

**Impact:** A SystemAdmin export may be stored, shared or attached to a ticket
and leaks secrets that were embedded in command templates. Transport and file
storage are outside the app's control.

**Fix:** Omit command scripts by default, redact known secret fields, or add an
explicit “include scripts” option with a warning. Treat the export as sensitive
data in the UI and docs.

**If skipped:** Secrets can leave the encrypted database through a support
file.

### OW-03 — Low — Local credential key can fall back to a plaintext file

**Evidence:** `InfraOrgITDesktop/electron/standalone.js:35-71` stores a
`safeStorage`-encrypted key when available; otherwise it writes
`credential-key.bin.fallback` with mode `0600` and shows a warning in Settings.

**Impact:** SSH credentials are still AES-GCM encrypted, but the key is readable
by the same OS user and by any backup that captures `userData`. The OS account
is already the local trust boundary, so this is a low-risk downgrade, not a
remote vulnerability.

**Fix:** Prefer the OS keychain; if unavailable, require an explicit operator
confirmation before storing the key or block local credential use. Keep the
current warning visible.

**If skipped:** A local backup can expose both ciphertext and key.

### OW-04 — Low — Import checksum is integrity, not authenticity

**Evidence:** `DataTransferEndpoints.cs:199-205` compares a SHA-256 stored
inside the same JSON document. Anyone who can edit the file can recompute the
checksum.

**Impact:** The checksum catches truncation/corruption but does not prove the
file came from a trusted instance. The import is SystemAdmin-only and shows a
preview, so exploitation requires convincing an administrator to import a
crafted file.

**Fix:** Label the checksum as corruption detection, and add a signed export
manifest or a detached signature when exports are used across trust boundaries.

**If skipped:** A malicious export can introduce command templates/actions that
the administrator later runs.

### Accepted residuals

- **D7 inventory read model:** any authenticated user and any `mcp:read` token
  can read the whole inventory; RBAC metadata is SystemAdmin-only. Accepted for
  the current product; revisit for multi-team or externally shared MCP.
- **MFA optional:** `KEYCLOAK_MFA=false` is the default; administrators must
  enable it operationally. Password policy is enforced in deploy.
- **Local standalone HTTP:** loopback-only, random port, per-launch bootstrap
  secret and CSRF; OS account is the trust boundary. Do not bind the sidecar to
  a LAN interface.
- **Dev stack credentials and public 8443:** local development only; deploy
  preflight and `WEB_BIND=127.0.0.1` cover production.
- **Unsigned packages:** tracked by OW-01; no release signing keys are
  configured in the repository.

  (API 63 unit + 111 integration; Web 228; Desktop 85; e2e 10/10).

  `SameSite=Lax`.
- TLS 1.1 rejected; HSTS/CSP/frame/referrer headers present.
- `dotnet list package --vulnerable --include-transitive`, `yarn audit --level
  high`, `npm audit --omit=dev`: no known vulnerabilities.

### Test-harness fixes

`scripts/security-smoke.py` now recognizes the agent-consent response
(`agent_approval_required`/`permission_required`) as a denied action instead of
a success, and allows the target metadata fields `clientAuth`, `credentialId`
and `hostKeyFingerprint`. These were false positives, not app bypasses.
